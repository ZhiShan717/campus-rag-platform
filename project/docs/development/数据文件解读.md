更新日期：2026-11-07　维护：戴月
面向：组长评审、组内交接、答辩演示

本文解释 `project/database/mysql/seeds/` 下每个数据文件是什么、为什么这么设计、数据怎么进数据库。看完这份，别人接手不用再问。

---

## 一、一句话总览

一共 **9 个 JSON + 1 个 SQL + 3 个脚本**，描述的是一套「制度 → 版本 → 条款」三层结构的数据：

| 层 | 是什么 | 数量 | 对应文件 |
| --- | --- | --- | --- |
| 清单 | 所有制度的目录 | 1 | `_index.json` |
| 制度 | 每份制度及其全部版本 | 8 | `d001`—`d008` |
| 版本 | 制度的历史版本（含状态、生效/失效日） | 10 | 嵌在上面的 `versions` 里 |
| 条款 | 可被检索的最小单位 | 43 | 嵌在 `versions[].chunks` 里 |

43 条条款正文合计 1,602 字，平均每条 37 字——这是刻意的：太长会检索不准，太短会丢上下文。

## 三、单个制度文件长什么样

以 `d001` 为例，结构固定为两段：`document`（制度本身）+ `versions`（版本数组）。

```text
{
  "document": { 编号、标题、文号、发布单位、类别、来源性质 },
  "versions": [
    {
      "id": "v001", "status": "SUPERSEDED",      ← 旧版，已被替代
      "effective_date": "2021-09-01",
      "expiry_date": "2024-08-31",
      "replaced_by": "v002",                      ← 被哪一版替代
      "chunks": [ 条款 1, 条款 2, … ]
    },
    {
      "id": "v002", "status": "ACTIVE",           ← 现行版本
      "effective_date": "2024-09-01",
      "chunks": [ … ]
    }
  ]
}
```

四个状态的含义：

| status | 含义 | 能进检索吗 |
| --- | --- | --- |
| `ACTIVE` | 现行有效 | 能 |
| `SUPERSEDED` | 已被新版替代 | 不能，但历史能查 |
| `ABOLISHED` | 已废止 | 不能 |
| `PENDING` | 已发布、未到生效日 | 不能 |

## 四、五个「为什么这么设计」

**1. 为什么把「版本」单独做一层，而不是一份制度一行？**

因为要回答「新规出来了，旧规还能不能用」。如果只有一行，换版时要么覆盖旧数据（历史丢失），要么建两份制度（无法关联）。分层后，检索时先按状态筛版本，再在条款里匹配，规则集中在一处。

**2. 为什么主键用 `d001`/`v001`/`c001` 而不是自增 1、2、3？**

自增 ID 在不同电脑导入后对不上，测试题里写的 `c008` 到别人机器可能变成别的条款。业务 ID 全局稳定，跨机器、跨环境一致，也让测试用例可读。

**3. 为什么 JSON 和 SQL 各存一份，不是只留 SQL？**

JSON 是唯一事实来源，SQL 由脚本生成（`tools/export_seed_sql.py`）。改数据只改 JSON，再重新生成 SQL。如果只留 SQL，改一个字段要手工编辑几百行 INSERT，容易出错也没法自动校验。

**4. 为什么故意放一份「已废止」和一份「未生效」？**

这是两道必答题的素材：q05 问国家助学金（已废止），q06 问勤工助学（未生效）。正确答案都是「没有依据」。没有这两份数据，就测不出系统会不会拿废纸当依据——这正是评审最想看的点。

**5. 为什么条款正文里要重复写「金额」「条件」这些词？**

因为检索是按字面匹配的。早期版本只写「每人每年 5000 元」，问「金额是多少」就检索不到；改成「奖励金额为每人每年 5000 元」才能命中。条款正文要自带字段名，这是实测踩出来的。

## 五、数据怎么进数据库

```text
JSON（源）──脚本──> SQL（INSERT）──> MySQL 三张表
     │
     └──脚本──> 数据自检（结构/状态/日期）＋ 检索自测（12 题）
```

三张表：`documents`（8 行）→ `document_versions`（10 行）→ `chunks`（43 行），外键自上而下。

导入命令（表建好后）：

```powershell
mysql -h 127.0.0.1 -P 13306 -u campus_dev -p campus_rag < .\project\database\mysql\seeds\demo-policies.sql
```

SQL 里用的是 `DELETE ... WHERE id LIKE 'd%'` 再 `INSERT`，所以可以重复执行，不会产生重复数据。

## 六、三个脚本各管什么

| 脚本 | 作用 | 什么时候跑 |
| --- | --- | --- |
| `validate_seed_data.py` | 校验结构、主键唯一、外键能解析、状态齐全、日期合法、每份制度最多一个 ACTIVE、与 `_index.json` 一致 | 每次改完数据 |
| `selfcheck_retrieval.py` | 用最朴素的二字词匹配跑 12 道题，检查题目与数据自洽 | 每次改完题目或条款 |
| `export_seed_sql.py` | 从 JSON 生成 SQL | 每次改完数据 |

三个都是退出码 0 表示通过，可以直接接到提交前检查。

## 七、30 秒口头版（评审时照着说）

> 这套数据分三层：制度、版本、条款。8 份制度、10 个版本、43 条条款，覆盖现行、已被替代、已废止、未生效四种状态。
> 检索时先按版本状态过滤，再在条款里匹配，所以新版出来旧版立刻失效，废止的制度不会被当依据。
> 数据以 JSON 为唯一来源，SQL 由脚本生成，改一处不会两边不一致。
> 另外配了 12 道题、一个数据自检脚本和一个检索自测脚本，都是能跑出结果的，不是只有文档。

## 八、可能被追问的问题

**Q：为什么只有 8 份制度，不是更多？**
A：够覆盖四种状态和四个业务类别即可。演示的重点是版本与引用规则，不是数据量。题目 12 道也按同样比例配比。

**Q：43 条条款是不是太少？**
A：单份 3—5 条，是能支撑一次完整问答的最小集。条款越多，越容易掩盖检索精度问题。

**Q：为什么不直接爬真实制度？**
A：真实文件有版权和引用风险，且格式不统一。现在全部标注为「虚构演示数据」，来源性质写在 `source_type` 和 `source_note` 里，对外不会误认。

**Q：数据改坏了怎么办？**
A：`SNAPSHOT.md` 里记了每个文件的 SHA256，重跑一次脚本就知道哪里不对；JSON 在 Git 里，随时可以回退。
