# 版本状态边界用例表（10.28）

更新日期：2026-10-28　维护：戴月
用途：把「哪种版本能进检索、哪种必须排除」写成可执行的用例，供 Java 版本过滤、Python 检索和验收共用。

---

## 一、先定一条规则：时间区间怎么算

建议采用**左闭右开**：一个版本在 `effective_date ≤ 今天 < expiry_date` 时有效。

| 日期关系 | 是否有效 | 理由 |
| --- | --- | --- |
| 今天 = effective_date | 有效 | 生效当天应可查 |
| 今天 = effective_date - 1 天 | 无效 | 还没生效 |
| 今天 = expiry_date - 1 天 | 有效 | 失效前一天仍有效 |
| 今天 = expiry_date | **无效** | 失效当天即失效，与「新版生效当天接管」对齐 |

> 这条需要沈明昊确认后写进代码。若改为闭区间（`≤ expiry_date` 仍有效），在换版当天会出现新旧两版同时有效，q03/q04 必然命中两条，题目就得改。**建议维持左闭右开。**

数据取自 `project/database/mysql/seeds/demo-policies/`。

| 编号 | 场景 | 数据条件 | 期望可检索 | 期望排除 | 判定依据 |

| B01 | 现行版本、在有效期内 | `v002` ACTIVE，今天 2026-10-29 | c006—c010 | v001 全部（c001—c005） | 状态过滤 |

| B11 | 服务器时区不是东八区 | 服务器 UTC，本地 2026-10-29 07:00 | 与东八区结果一致 | — | 日期比较必须用同一个时区算「今天」 |
| B12 | 跨版本引用一致性 | 历史记录里引用了 `c003`（旧版） | 历史详情仍能展开旧版原文 | 不参与新检索 | 快照不随版本更新而改变 |

## 三、B03 / B11 两个坑的说明

**B03**：如果系统只按 `status` 判断，不做日期回放，那么"2024-08-31 那天适用哪一版"这类历史问题就无法回答。首周可以先不做日期回放，但要在文档里写明"检索基于当前状态"，避免验收时被问住。一旦要做，`status` 就必须由 `effective_date/expiry_date` 实时推导，不能手工维护。

**B11**：日期比较最容易出的 bug 是"服务器算今天用 UTC，用户在东八区"。表现是每天 0:00—8:00 之间，新版会比预期早 8 小时生效或旧版晚 8 小时失效。验收时挑一个早上的时间点复跑一次 B02。

## 四、判定口径

- 每个用例只看两件事：**该命中的有没有全部命中**、**该排除的有没有混进来**。
- 「排除集合」为空表示该场景不涉及排除，不代表不用检查。
- 任一用例失败，先确认是数据问题还是过滤逻辑问题：数据问题改 seeds，逻辑问题提给沈明昊。
