### 模型约定

- 嵌入模型：`BAAI/bge-large-zh-v1.5`，输出 **1024 维**；后续 Elasticsearch `dense_vector.dims` 必须一致。手册的 768 维不适用于该 large 模型，当前尚未创建业务索引。
- 重排模型：`BAAI/bge-reranker-base`。
- 本地生成模型：Ollama `qwen3:1.7b`，用于开发联调；团队统一模型或 API 尚未确定。
- 负责人已通过中文嵌入相关性、重排和带引用标记的构造材料生成检查；这不代表完整业务 RAG、权限或评测已通过。
- 权重不在 Git 中。各成员按需运行模型准备脚本自行下载；CPU 安装入口会校验依赖包，模型下载会固定来源并校验权重。参数模板见 [model-env.example](../environment/model-env.example)。

## 队员本机准备

现有入口首先服务于负责人电脑，**尚未完成其他电脑上的整套安装验收**。克隆不会带上已安装软件、模型或服务数据。

1. 安装 Git、VS Code、JDK 17、Maven、Python 3.11、Node.js 和支持 Linux 容器的 Docker Desktop；需要本地生成模型时安装 Ollama。Windows 应先满足 Docker 的 WSL2 要求。
2. 按自己的安装位置检查并调整 [Enter-DevEnvironment.ps1](../environment/Enter-DevEnvironment.ps1) 和 [VS Code 工作区](../environment/校园RAG开发环境.code-workspace)。其中 Java、Maven、Node.js、Git、VS Code 等仍含负责人的 D 盘路径。GitHub Desktop 辅助入口也含本机路径，不属于队员必需工具。
3. 先核对 [Start-ContainerEngine.ps1](../environment/Start-ContainerEngine.ps1)：它为负责人设置项目内 Docker 独立配置和数据目录。已有 Docker 数据的成员应先明确复用方式，避免将不同配置对应的容器误认为丢失。不要直接复制负责人的 Docker 配置目录或数据盘。
4. 在仓库根目录，用已安装的 Python 3.11 创建独立虚拟环境，再安装 SDK：

```powershell
py -3.11 -m venv .venv
.\environment\Install-PythonDependencies.ps1
```

5. 完成上面的路径与 Docker 配置核对后，在仓库根目录运行：

```powershell
# 默认启动 MySQL、Redis、Elasticsearch、MinIO、Nacos 五项服务
.\environment\Start-Services.ps1
.\environment\Initialize-ApplicationEnvironment.ps1
.\environment\Check-Environment.ps1
.\environment\Test-Services.ps1

# 需要消息队列时，改用完整七项服务启动与检查
.\environment\Start-Services.ps1 -Messaging
.\environment\Test-Services.ps1 -Messaging
```

6. 负责模型或 RAG 联调的成员，按需下载并验证本地模型：

```powershell
.\environment\Prepare-Models.ps1
# 已安装、已下载后，可单独重新检查
.\environment\Test-Models.ps1
```

基础服务启动时会调用 [Initialize-Environment.ps1](../environment/Initialize-Environment.ps1)，在**该成员本机**生成随机凭据；重复运行保留原值。[Initialize-ApplicationEnvironment.ps1](../environment/Initialize-ApplicationEnvironment.ps1)再汇总连接参数并生成独立 APP/JWT 密钥。未来业务代码需要将这些变量对应到实际配置。

负责人日常可以使用 `environment/启动负责人环境.cmd` 等入口；队员须先完成上述本机适配。工作区文件也位于 `environment/`，打开后仍在仓库根目录开发。根目录 `.local/`、`.venv/`、`.setup/` 属于各自的本机运行区，不由 Git 分享。无需本地模型的成员，可先只准备自己负责模块所需的工具与服务。

## 代码协作

建议团队采用以下简单流程，分支命名和合并规则可由负责人进一步确认：

```powershell
git switch main
git pull --ff-only
git switch -c feat/自己的任务名
# 完成修改、运行对应检查后，只添加本次需要的文件；将示例 README.md 换成实际修改的路径
git add "README.md"
git commit -m "描述本次修改"
git push -u origin feat/自己的任务名
```

随后向 `main` 提交 Pull Request，说明改动和检查结果，请负责人或相关队员审查后合并。共享接口、数据表、索引维度、依赖版本或环境变量有变更时，同步更新说明。不要提交模型、虚拟环境、数据卷、安装包、缓存和本机凭据。
