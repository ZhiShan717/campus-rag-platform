# 校园 RAG 知识库平台：详细安装与配置指南

版本日期：2026-10-23。适用 Windows x64、Java 17、Python 3.11 与 Docker Linux 容器。依据原始 7 页手册及仓库提交 ee25619 编写，软件版本表示项目记录基线，不表示官方最新版。后续代码变更以仓库现行 README、POM、依赖锁和 Compose 为准。

## 01 使用范围与完成目标

本指南供项目负责人和新队员逐步配置开发环境。项目采用 Java 微服务、Python RAG 运行时与 Vue 前端；目标链路是文档上传、对象存储、解析分块、向量入库、混合检索、版本与权限过滤、重排，以及带引用的回答。

**当前可完成：**开发工具安装，仓库克隆，Python SDK 安装，五项或七项中间件启动，中文分词和认证检查，三类模型准备，以及 Maven 聚合结构验证。

**当前不能完成：**直接启动业务网站、Java 业务服务、Python API、前端页面或完整问答链路。仓库仍为目录骨架，没有 Java 启动类、Python API 入口、前端 package.json、业务表及 ES 索引定义。

| 路线 | 适用对象 | 本指南中的操作 |
| --- | --- | --- |
| 新队员首次安装 | 新电脑或新克隆 | 按 02-14 节执行；Docker 优先采用 09 节，复用本人已有 Desktop |
| 负责人已有环境 | D:\campus_RAG_work 已配置电脑 | 不重装、不重建虚拟环境、不重置凭据；重点看 15-17 节 |
| 业务开发与联调 | 模块工程实现后 | 18-19 节是后续建设与验收标准，不是当前已实现功能 |

全文命令默认在对应仓库根目录的 PowerShell 执行。出现“管理员 PowerShell”时才使用管理员窗口。每个代码块按顺序执行，遇到错误先停下排查，不应跳过失败步骤继续启动。

新队员 Docker 路线来自对脚本依赖的审核，尚未在另一台全新电脑完成端到端安装验收。请按实际安装路径和 Docker 状态核对，不能把克隆等同于自动安装。

安装顺序：Windows/WSL2 → Git/VS Code → JDK/Maven → Python/Node → Docker/Ollama → 克隆仓库 → 路径和 Docker 客户端适配 → SDK → 中间件 → 模型 → 分层验收。

## 05 Windows、虚拟化与 WSL2

1. 在任务管理器的“性能 / CPU”查看“虚拟化”是否已启用。未启用时，在 BIOS/UEFI 开启 Intel VT-x 或 AMD-V；具体入口按电脑厂商说明。
2. 使用仍受支持的 Windows 版本并安装必要更新。以管理员身份打开 PowerShell，为 Docker 准备 WSL；下面的方式不额外安装 Ubuntu。[S02]

```powershell
# 管理员 PowerShell：首次启用 WSL
wsl --install --no-distribution
```

3. 按提示重启电脑。重新打开管理员 PowerShell，更新 WSL 并将新发行版默认设为版本 2。[S03]

```powershell
wsl --update
wsl --set-default-version 2
wsl --version
wsl --status
wsl -l -v
```

成功标准：WSL 版本满足 Docker 当前要求；系统虚拟化可用。只为 Docker 使用 WSL2 时，不要求额外创建个人 Ubuntu 发行版，列表中没有 Ubuntu 不等于安装失败。

如果旧系统不识别 wsl --install 或 --version，先按微软文档完成系统 / WSL 更新。公司或学校设备的功能安装被策略限制时，应由设备管理员按策略处理。

此阶段不需要安装独立的 MySQL、Redis、ES 或 Nacos Windows 服务；后续由项目 Compose 提供，避免重复安装占用端口。

## 07 JDK 17 与 Maven

1. 从 Eclipse Temurin 官方页面选择 Java 17、Windows、x64、JDK 安装包，避免下载成只有运行时的 JRE。[S06] MSI 的自定义安装选项可启用 Add to PATH 和 Set JAVA_HOME。
2. JAVA_HOME 指向 JDK 根目录，值中不要包含 bin；PATH 添加 %JAVA_HOME%\bin。安装后重新打开终端验证。
3. 从 Maven 官方下载项目约定的 3.9.x Binary zip，已验证基线为 3.9.9；解压到自己的工具目录，将其 bin 加入 PATH。[S07] 不要选择 Source archive。

```powershell
java -version
javac -version
mvn -version
```

成功标准：java 和 javac 均为 17，Maven 能启动且报告使用 Java 17。Maven 只是命令行工具，解压即可，不需要 Windows 服务。

| 配置 | 示例值及含义 |
| --- | --- |
| JAVA_HOME | 例如 D:\devtools\jdk-17；使用自己的实际 JDK 根目录 |
| MAVEN_HOME | 例如 D:\devtools\apache-maven-3.9.9；仓库开发终端会使用此项 |
| PATH | 包含上述 JDK 的 bin 以及 Maven 的 bin；重新打开终端后生效 |

**还需核对项目脚本：**environment/Enter-DevEnvironment.ps1 每次运行会将 JAVA_HOME 设为 D:\JDK，将 MAVEN_HOME 设为 D:\maven\apache-maven-3.9.9-bin\apache-maven-3.9.9。若本机路径不同，必须在本机核对并调整对应赋值；只设置系统环境变量仍可能被脚本覆盖。

该脚本还列有 Node、Git、VS Code 的 D 盘路径候选。候选不存在时可继续使用系统 PATH 中的安装，但应以 Get-Command 和工具版本的实际结果确认。纯个人路径调整不混入业务提交；需要团队共享的可移植性改进应单独审查。

## 08 Python、Node.js 与虚拟环境

1. 安装 Python 3.11 x64，选择完整安装器并保留 pip 与 Python Launcher；不要使用 embeddable zip。Windows 安装说明与 3.11.9 兼容基线下载见 [S08]。
2. 安装时可勾选 Add python.exe to PATH，但后续仍用 py -3.11 明确选择版本，避免电脑上已有 Python 3.12/3.14 时选错。
3. Node.js 使用团队约定的 24.x 基线或后续前端包锁要求；官方安装包包含 npm。[S09] 前端尚无工程入口，安装工具不等于应用可启动。

```powershell
py --list
py -3.11 --version
node --version
npm.cmd --version
```

4. 在新克隆仓库根目录创建一次虚拟环境。负责人已有 .venv 时不要重建，先检查已有解释器。

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip --version
```

成功标准：虚拟环境解释器报告 Python 3.11，pip 路径位于本仓库 .venv。模型 CPU 安装脚本固定 cp311-win_amd64，不能用 Python 3.12 或 ARM64 解释器直接替代。

后续不必激活环境，也能使用完整路径调用 .venv\Scripts\python.exe。PowerShell 若阻止 npm.ps1，使用 npm.cmd；若阻止项目 .ps1 且设备策略允许，可只在当前窗口使用 Set-ExecutionPolicy -Scope Process Bypass，不改全局策略。

## 09 Docker Desktop 安装与客户端适配

先从 Docker 官方 Windows 入口安装 Desktop，选择 WSL2 后端，打开后确认使用 Linux containers。[S01] 用本人 Windows 开始菜单启动自己的 Docker Desktop，等待引擎就绪。

在普通 PowerShell 中验证 docker version 的 Client 和 Server 都能返回，docker compose version 可用，docker info --format '{{.OSType}}' 返回 linux。安装器退出不等于引擎已经运行。

**新队员采用本节路线：**复用本人已启动的 Desktop 引擎，只建立项目独立的 CLI 配置，不调用会切换独立数据目录的 Start-ContainerEngine.ps1。下面命令在仓库根目录执行。[S10]

```powershell
$env:DOCKER_CONFIG = Join-Path (Get-Location) '.local\docker-cli'
$env:DOCKER_CONTEXT = $null
$env:DOCKER_HOST = $null
$env:DOCKER_TLS_VERIFY = $null
$env:DOCKER_CERT_PATH = $null
.\environment\Initialize-ContainerClient.ps1

$contexts = @(docker context ls --format '{{.Name}}')
if ($LASTEXITCODE -ne 0) { throw 'Cannot list Docker contexts' }
if ('desktop-linux' -notin $contexts) {
    docker context create desktop-linux `
        --docker 'host=npipe:////./pipe/dockerDesktopLinuxEngine'
    if ($LASTEXITCODE -ne 0) { throw 'Cannot create Docker context' }
}
$env:DOCKER_CONTEXT = 'desktop-linux'
docker context inspect desktop-linux --format '{{.Endpoints.docker.Host}}'
docker info --format '{{.OSType}}'
docker compose version
```

上述 named pipe 是 Windows Docker Desktop Linux 引擎的常见端点；如本机不是该端点或检查失败，应先在本人原 Docker 配置下检查 context inspect 的实际 Host，不要强行替换已存在的 context。成功标准是目标为自己的本机 Linux 引擎，而不是远程服务器或 Windows containers。

插件初始化脚本会寻找仓库内 .local\DockerDesktop\resources\cli-plugins，以及 %LOCALAPPDATA%\Programs\DockerDesktop\resources\cli-plugins、%ProgramFiles%\Docker\Docker\resources\cli-plugins。若 Docker 装在其他位置，需按真实安装路径适配候选目录。

## 10 SDK 安装与本机参数初始化

完成 Python 虚拟环境后，从仓库根目录安装 SDK。安装脚本使用 SDK 锁文件、运行依赖一致性检查和离线调用检查，不启动业务 API。

```powershell
.\environment\Install-PythonDependencies.ps1
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe .\environment\Test-PythonDependencies.py
```

成功标准：pip check 无依赖冲突，SDK 检查报告 PASS。优先按 requirements-rag.lock.txt 安装，不执行未经团队确认的整套升级，也不执行原手册的 pip install -e .：当前没有对应 pyproject.toml。

初始化基础服务凭据。该步骤只在本机生成 environment/.env；重复执行保留已有值，不轮换已有数据库中的密码。

```powershell
.\environment\Initialize-Environment.ps1
Test-Path -LiteralPath '.\environment\.env'
```

成功标准：文件存在，脚本报告已有或新建凭据已保护。不要把文件正文输出到群聊、Issue、截图或共享日志。该文件与持久化数据卷配套保管。

| 文件 | 内容及维护方式 |
| --- | --- |
| requirements-rag.in / .lock.txt | SDK 依赖声明与固定安装清单；日常使用锁文件 |
| requirements-models.in / .lock.txt | 模型依赖声明与固定清单；安装时同时遵守 SDK 约束 |
| environment/.env | 服务随机凭据，只留本机 |
| environment/.env.application | 服务连接参数、模型路径与随机 APP/JWT 密钥，后续生成 |

同一 Docker 引擎的 Compose 项目名固定为 campus-rag-dev。另一份克隆仍可能连接同名数据卷；不要以为换目录就创建了独立空数据库，更不要用新密码覆盖旧卷对应的凭据。

## 11 新队员启动五项或七项基础服务

本节接着 09 节已连接本机 Linux 引擎的终端执行。加载 Common.ps1 后，将继续使用项目独立 Docker CLI 配置与 desktop-linux；它提供固定项目名、Compose 文件和环境文件的参数。

```powershell
. .\environment\Common.ps1
$composeArgs = @(Get-CampusComposeArguments)
# 需要 RocketMQ 时，上行改为：
# $composeArgs = @(Get-CampusComposeArguments -Messaging)

docker @composeArgs config --quiet
if ($LASTEXITCODE -ne 0) { throw 'Compose validation failed' }
docker @composeArgs up --detach --build --wait --wait-timeout 600
if ($LASTEXITCODE -ne 0) { throw 'Infrastructure startup failed' }
Set-CampusNacosPassword
```

默认启动 MySQL、Redis、Elasticsearch+IK、MinIO、Nacos 五项；Messaging 增加 NameServer 和 Broker 两项长期服务。消息卷权限初始化是一次性辅助容器，不算业务服务。

此方式直接使用共用 Compose，不执行负责人独立 Docker Desktop 数据目录启动器。镜像首次拉取和 IK 构建可能较久；网络失败时先检查官方镜像源连通性或本人 Docker 登录，不修改镜像为未经核实的任意来源。

随后按所选范围验收并生成应用参数：

```powershell
.\environment\Test-Services.ps1
# 若已启用消息组件，改用：
# .\environment\Test-Services.ps1 -Messaging
.\environment\Initialize-ApplicationEnvironment.ps1
docker @composeArgs ps
```

成功标准：所选服务均 healthy；MinIO、Nacos、ES 认证和 IK 分词通过；Messaging 时 Broker 真实注册检查通过。Nacos 使用独立 Derby 卷，不要求先创建 campus_rag 业务表。

业务连接参数在 environment/.env.application，实际应用仍需实现变量映射和配置加载。初始化文件本身不会创建 Java/Python 服务，也不会创建业务表或 ES 索引。

BAAI 官方 large 中文模型输出 1024 维，原手册的 768 维不适用于本模型。[S13] 业务 ES dense_vector.dims 必须与实际输出一致；不要截断向量凑成 768。重排模型用于候选排序，不能代替向量模型。

```powershell

$body = @{
    model = 'qwen3:1.7b'
    prompt = '请用一句中文说明你已准备好。'
    stream = $false
    think = $false
    keep_alive = 0
    options = @{ num_ctx = 2048; num_predict = 120 }
} | ConvertTo-Json -Depth 4

    -Uri 'http://127.0.0.1:11434/api/generate' `
    -ContentType 'application/json; charset=utf-8' `
    -Body ([Text.Encoding]::UTF8.GetBytes($body))
$result.response
```

该请求仅验证模型 API，不验证检索与引用。keep_alive=0 要求请求后卸载生成模型，但其他模型或托盘服务仍可能占用内存。

## 19 RAG、引用、版本与权限验收标准

以下标准来自原手册，并修正维度及目录；应在业务功能实现后验收，当前不宣称已通过。

| 验收项 | 操作与通过标准 |
| --- | --- |
| 上传与索引 | 用可公开的构造 PDF 上传，跟踪解析、切分、向量化与 ES 入库；原手册目标为两分钟内 doc_chunk 可检索，chunk_count 与记录一致，最终指标由团队落实 |
