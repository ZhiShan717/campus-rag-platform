### 模型约定

- 嵌入模型：`BAAI/bge-large-zh-v1.5`，输出 **1024 维**；后续 Elasticsearch `dense_vector.dims` 必须一致。手册的 768 维不适用于该 large 模型，当前尚未创建业务索引。
- 重排模型：`BAAI/bge-reranker-base`。
- 本地生成模型：Ollama `qwen3:1.7b`，用于开发联调；团队统一模型或 API 尚未确定。
- 负责人已通过中文嵌入相关性、重排和带引用标记的构造材料生成检查；这不代表完整业务 RAG、权限或评测已通过。
- 权重不在 Git 中。各成员按需运行模型准备脚本自行下载；CPU 安装入口会校验依赖包，模型下载会固定来源并校验权重。参数模板见 [model-env.example](../../environment/model-env.example)。

## 队员本机准备

现有入口首先服务于负责人电脑，**尚未完成其他电脑上的整套安装验收**。克隆不会带上已安装软件、模型或服务数据。

1. 安装 Git、VS Code、JDK 17、Maven、Python 3.11、Node.js 和支持 Linux 容器的 Docker Desktop；需要本地生成模型时安装 Ollama。Windows 应先满足 Docker 的 WSL2 要求。
2. 按自己的安装位置检查并调整 [Enter-DevEnvironment.ps1](../../environment/Enter-DevEnvironment.ps1)，其中 Java、Maven、Node.js、Git、VS Code 等仍含原本机路径。编辑器直接打开仓库根目录，按本人安装配置解释器和 Java 工具。负责人个人工作区和账号登录辅助不随 Git 分发。
3. 先核对 [Start-ContainerEngine.ps1](../../environment/Start-ContainerEngine.ps1)：它为负责人设置项目内 Docker 独立配置和数据目录。已有 Docker 数据的成员应先明确复用方式，避免将不同配置对应的容器误认为丢失。不要直接复制负责人的 Docker 配置目录或数据盘。
4. 在仓库根目录，用已安装的 Python 3.11 创建独立虚拟环境，再安装 SDK：

```powershell
py -3.11 -m venv .venv
.\environment\Install-PythonDependencies.ps1
```

5. 完成上面的路径与 Docker 配置核对后，在仓库根目录运行：

```powershell
# 默认启动 MySQL、Redis、Elasticsearch、MinIO、Nacos 五项服务
.\environment\Start-Services.ps1
.\environment\Initialize-ApplicationEnvironment.ps1
.\environment\Check-Environment.ps1
.\environment\Test-Services.ps1

# 需要消息队列时，改用完整七项服务启动与检查
.\environment\Start-Services.ps1 -Messaging
.\environment\Test-Services.ps1 -Messaging
```

6. 负责模型或 RAG 联调的成员，按需下载并验证本地模型：

```powershell
.\environment\Prepare-Models.ps1
# 已安装、已下载后，可单独重新检查
.\environment\Test-Models.ps1
```

基础服务启动时会调用 [Initialize-Environment.ps1](../../environment/Initialize-Environment.ps1)，在**该成员本机**生成随机凭据；重复运行保留原值。[Initialize-ApplicationEnvironment.ps1](../../environment/Initialize-ApplicationEnvironment.ps1)再汇总连接参数并生成独立 APP/JWT 密钥。未来业务代码需要将这些变量对应到实际配置。

队员完成上述适配后，使用仓库中共用的 `Start-Services.ps1`、`Start-ModelService.ps1` 和 `启动开发终端.cmd` 等入口；负责人专用启动包装与编辑器配置只留本机。根目录 `.local/`、`.venv/`、`.setup/` 属于各自的本机运行区，不由 Git 分享。无需本地模型的成员，可先只准备自己负责模块所需的工具与服务。

## 代码协作

公开仓库的读取权限与写入权限分开。先根据本人是否有原仓库的写入权限选择下面一种流程；分支命名和合并规则可由负责人进一步确认。

### 已有原仓库写入权限

在已克隆的项目根目录运行。`origin` 应指向 `https://github.com/ZhiShan717/campus-rag-platform.git`，受邀队员先接受邀请，并使用本人 GitHub 账号认证：

```powershell
git switch main
git pull --ff-only origin main
$branch = "feat/knowledge-upload" # 换成自己的任务分支名
git switch -c $branch
# 完成修改、运行对应检查后，只添加本次需要的文件；将示例 README.md 换成实际修改的路径
git add "README.md"
git commit -m "描述本次修改"
git push -u origin $branch
```

随后在 GitHub 向原仓库的 `main` 提交 Pull Request，源分支为刚推送的任务分支，请负责人或相关队员审查后合并。

### 没有原仓库写入权限

1. 登录自己的 GitHub 账号，打开[项目仓库](https://github.com/ZhiShan717/campus-rag-platform)，点击 **Fork**，在个人账号下保留仓库名 `campus-rag-platform`。
2. 尚未克隆时，在计划存放项目的父目录运行，输入自己的 GitHub 用户名：

```powershell
$githubUser = Read-Host "请输入你自己的 GitHub 用户名"
git clone "https://github.com/$githubUser/campus-rag-platform.git"
cd campus-rag-platform
git remote add upstream https://github.com/ZhiShan717/campus-rag-platform.git
```

如果已经按前文克隆了原仓库，无需再次克隆。在现有项目根目录运行下面这组命令，将 `origin` 改为个人 Fork，并保留原仓库为 `upstream`；不要同时执行两组初始化命令：

```powershell
$githubUser = Read-Host "请输入你自己的 GitHub 用户名"
git remote rename origin upstream
git remote add origin "https://github.com/$githubUser/campus-rag-platform.git"
```

3. 在项目根目录同步原仓库并创建任务分支：

```powershell
git fetch upstream
git switch main
git merge --ff-only upstream/main
$branch = "feat/knowledge-upload" # 换成自己的任务分支名
git switch -c $branch
# 完成修改和检查后，将 README.md 换成实际修改的路径
git add "README.md"
git commit -m "描述本次修改"
git push -u origin $branch
```

4. 在 GitHub 创建跨仓库 Pull Request：目标仓库选择 `ZhiShan717/campus-rag-platform`，目标分支 `main`；来源选择自己的 Fork 及任务分支。推送个人 Fork 仍需本人账号认证，不需要原仓库写入权限。

两种方式都应说明改动和检查结果，经审查后合并。共享接口、数据表、索引维度、依赖版本或环境变量有变更时，同步更新说明。不要提交模型、虚拟环境、数据卷、安装包、缓存和本机凭据。公开仓库的代码、Issue 与 Pull Request 对外可见，测试材料应使用可公开的人工构造内容。
